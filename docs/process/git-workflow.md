# Git workflow, environments and CI/CD

## Branches

| Branch | Role | Environment | Protected |
| --- | --- | --- | --- |
| `main` | Integration of finished stories | CI only | yes |
| `test` | What the team/PO validates | Web "test" environment | yes |
| `prod` | What real users see | Web "prod" environment | yes |
| `us-<id>-<slug>` | One short-lived branch per user story | none | no |

## Flow

```text
us-011-grid ──PR──▶ main ──PR (release)──▶ test ──PR (release)──▶ prod
   (merge commit)      CI        (merge commit)  deploy test   (merge commit)  deploy prod
```

1. Pick the top **Ready** story; create `us-<id>-<slug>` from the latest `main`.
2. Commit often, messages follow `type(us-NN): description` (`feat(us-011): ...`).
3. Open a PR to `main`. CI must pass and at least one person other than the author approves.
4. Merge with a **merge commit** (squash and rebase merges are disabled). Delete the branch.
5. When a set of stories is ready to validate, open a release PR `main → test`. After merge, `test` deploys.
6. After the PO accepts it on `test`, open a release PR `test → prod`. After merge, `prod` deploys.
7. Only then start the next story (WIP = 1).

Hotfix: if `prod` is broken, branch from `prod`, PR to `prod`, then PR the same fix back into `main`.

## Protection rules (GitHub rulesets) for `main`, `test` and `prod`

- Require a pull request before merging; no direct pushes, no force pushes, no deletion.
- Require **1 approval**, dismiss stale approvals on new commits, require conversation resolution.
- Require status checks: `lint`, `security`, `test` (see CI below).
- No bypass actors (not even admins) once the team is comfortable.
- Repository settings: allow **merge commits only**; disable squash and rebase merging;
  automatically delete head branches.

## CI (every PR to `main`, `test`, `prod`)

| Job | Runs |
| --- | --- |
| `lint` | RuboCop, erb_lint, markdownlint-cli2, yamllint, cuke_linter, i18n-tasks, story/feature sync (`bin/check-stories`), commitlint on the PR's commits, Reek / rails_best_practices (advisory) |
| `security` | Brakeman, bundler-audit |
| `test` | RSpec, Cucumber (with Capybara), SimpleCov ≥ 90 % |

PRs to `test` and `prod` run the same checks again, so a bad promotion cannot slip through.

## CD

- Push (merge) to `test` → deploy to the test environment. Push to `prod` → deploy to prod.
- Secrets (`RAILS_MASTER_KEY`, `DATABASE_URL`, deploy tokens) live in GitHub Environments `test` and `prod`;
  `prod` can require a manual approval before the deploy job runs.
- Hosting is decided in [skeleton.md](../skeleton.md#hosting-options-free-first).

## Commit and PR conventions

- Commit: `feat(us-011): render grid by term` (imperative, English, focused). Types: `feat`, `fix`,
  `refactor`, `test`, `docs`, `chore`, `ci`, `build`, `perf`, `style`, `revert`. The scope is the story
  number in lowercase; Lefthook rejects anything else. Merge and revert messages generated by git pass.
- Author: `git config user.name` must be your first and last name; `.mailmap` unifies old identities.
- PR title = `type(us-NN): description`, like a commit; PR body links the story file and ticks the Definition of Done checklist
  (PR template in `.github/pull_request_template.md`).
